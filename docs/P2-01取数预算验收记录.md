# P2 01：读取过程中的行数与字节预算

日期：2026-10-20。本轮只完成 P2 01 的取数预算部分，保留既有未提交工作区；DatasetController、首屏与 COUNT 解耦、深分页体验仍留待后续。没有提交、推送、发布或替换现用 EXE。

## 已实现的行为

| 预算 | 默认值 | 处理方式 |
| --- | --- | --- |
| 行数 | 10,000 行 | 最多多读取一条原生行确认是否还有结果；恰好上限且正常结束不误标截断 |
| 结果字节 | 16 MiB | 计入列元数据、显示值、typed 原值的持有开销估算和紧凑 JSON 编码；超限前停止保留整行 |
| 原始单元格 | 1 MiB | 借用原始载荷检查，超限后不再进行 JSON、hex、Base64 等二次转换 |

统一实现位于 `database/result_budget.rs`。JSON 使用限额计数 writer，不先构造完整编码字符串；UTF-8、JSON 转义、二进制显示膨胀与 typed 原值均计费。预算拒绝一行时不消耗额度，不裁剪单元格、不填假 NULL、不将类型化值和显示行错位。

四驱动的普通 `query` 和 `query_typed` 均在读取过程中检查预算：

- **MySQL**：`query_iter/exec_iter` 后逐行 `next`，不再 `collect_and_drop` 收齐查询结果。正常完整消费才可沿用租约；截断、未读后续结果或流中错误会隔离物理 Conn，不能隐式排空巨大尾部。非查询 `execute` 改为逐步丢弃不可见返回行，避免无用的完整 Vec；它仍须完成原执行语义。
- **PostgreSQL**：预编译后使用 `query_raw` 的 RowStream，超限立即去活取消句柄并终止当前连接任务。本机 tokio-postgres 0.7.18 的响应通道为 `channel(1)`，消费暂停会形成背压。
- **SQL Server**：逐项读取 QueryStream，保留首结果元数据和行，不再用会收集全部结果的 `into_first_result`。遇第二结果或超限立即停读、丢弃 Client；完整读到流结束才允许同租约继续使用。
- **SQLite**：沿用工作线程逐行 stepping，补齐字节与单元格预检；离开读取循环即释放语句，保留原有逻辑会话的 TEMP/ATTACH/PRAGMA 语义。

继续复用 `QueryResult.truncated`，不改变 IPC 结构。该字段现在表示读取提前停止，可能是行、字节、单元格预算或未读取的后续结果；`totalCount` 仍是本次保留行数，不冒充全库精确总数。零行截断也保留列元数据并显示预算提示。

## 安全与能力边界

截断的受控表页面返回 `RESULT_BUDGET_EXCEEDED`，不会登记新结果上下文或行句柄。前端策略也明确拒绝截断结果编辑。普通 SQL、筛选、数据库版本/类型白名单、凭据、真实键、冲突和提交回执规则均不放宽。

提前关闭连接不等于用户取消、服务端已停止、事务已回滚或全部语句已执行。对于带副作用、RETURNING 或多语句的原始 SQL，不能从 `truncated` 推断提交结果；需要完整脚本执行语义时沿用显式批执行路径。

**本预算约束应用保留结果与后续编码，并非进程 RSS 硬上限。** 数据库库会先解码单个协议行，Tiberius 的大 PLP 字段还可能按声明长度分配；公开读取 API 无法在该分配之前检查载荷。网络缓冲、协议解码、数据库自身执行内存和其他并发任务不包含在这 16 MiB 内。首屏/峰值 RSS 基准测试尚未完成，不能把预算常量当成性能实测成绩。

导出、SQL 转储和元数据专用通道没有在本轮一并改为有界流式实现；它们分别属于 P2 02/03，不能因查询已改造便声称所有取数路径都有该预算。
